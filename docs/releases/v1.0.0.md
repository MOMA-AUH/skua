# Skua 1.0.0 migration and release notes

Release preparation: this document accompanies the v1.0.0 candidate. Publication
requires the validation gates below. See the [v1 contract](../v1-contract.md)
for the supported API, workflow, fields and compatibility policy.

## Changes from 0.8.2

Version 1.0.0 establishes a compatibility contract for the existing annotation
workflow and top-level Python exports. Package and Conda descriptions now call
Skua an evidence annotator for supplied small variants; development status is
`Production/Stable`. Candidate discovery, automatic FILTER decisions,
multiallelic scoring, UMI consensus generation and internal parallel execution
are outside the initial contract.

**Model scores are now reported only for assessed evidence.** Earlier releases
retained numeric scores on `INSUFFICIENT_EVIDENCE` results, including a
prior-derived posterior at zero case depth. Version 1.0.0 reports both the log
Bayes factor and artifact posterior as missing (`.`) in VCF, `None` in Python
`Stats`, and `null` in JSON for every failed assessment. Counts, input priors,
status and reasons remain available. Evidence collection and numeric scores
for `ASSESSED` results are unchanged.

Python callers must now handle `float | None` for both score fields, and JSON
consumers must handle `null` before numerical comparisons. Reannotate old
outputs to apply this behavior; use `--force` for existing Skua annotations and
reindex compressed VCF output afterwards. Threshold changes may now make
scores missing. This change does not require rebuilding a compatible PON.

`SKUA_ASSESSMENT_REASONS` is now present on every supported model-annotated VCF
record, with value `.` when the case is assessed or a reason list otherwise.
This replaces v0.8.2's omission of the field on assessed records and keeps the
assessment FORMAT fields consistent. Unselected samples also have `.`;
unsupported records and case-only outputs still have no assessment fields.
Python/JSON reasons remain an empty tuple/list when assessed.

The producer version in run/PON metadata becomes `1.0.0`; PON schema
remains **2**, evidence policy **8**, and run-summary schema **1**. Valid 0.8.2
PONs with those versions remain usable without rebuilding. Validate them before
reuse; this release does not make invalid or incompatible inputs valid.

## Migrating from earlier 0.x releases

The following summarizes the current behavior, including fixes from earlier
0.x releases and the v1 score-availability change above. Re-run annotation
when old outputs used different evidence or
scoring behavior; do not assume that old scores can be relabeled as v1 results.

| Area | Current behavior and migration action |
| --- | --- |
| Python imports | Use documented exports from `skua`. Submodule helpers (including row formatters and statistical helpers) are outside the compatibility promise. |
| JSON shape | Annotation wrappers return an object with `run_summary` and `records`, replacing the older bare list. Read `json.loads(payload)["records"]`. Wrappers still use all case read groups and a constant model prior; isolate the case upstream. |
| Sample identity | VCF writers isolate the selected sample's assigned RGs. Normal files must represent distinct named samples; duplicate inputs and case membership are rejected. Merge libraries for the same normal upstream and exclude the case from its panel. |
| Read evidence | Missing query names count as unusable diagnostics; MNVs cannot bridge internal insertions/deletions/skips. Proper-pair, SAM-flag and fragment rules apply to case and normals. MAPQ 255 passes the numeric threshold (the earlier special exclusion was removed). Old policies require rebuilding. |
| Indels | Policy 8 recognizes equivalent CIGAR placements within 100 bases when a FASTA is supplied, subject to spanning/quality constraints. Build with `--reference` for this mode; exact-anchor PONs keep their stored mode. Target joins still require exact allele keys. |
| Dispersion | Since 0.8.0, both counts and depths in the estimator use the same retained normals. Reannotate scores from earlier versions when normals were excluded. This scoring correction alone does not require a PON rebuild, but an obsolete evidence policy still does. |
| Assessment | Check `SKUA_ASSESSMENT_STATUS` / `Stats.assessment_status` before interpreting scores. Ineligible sites retain counts and reasons but have missing model scores (`.` / `None` / `null`). `ANNOTATED` is not an eligibility decision. Assessed VCF records retain `SKUA_ASSESSMENT_REASONS` with value `.`; Python/JSON reasons are empty. |
| Parameters and priors | Nonfinite/out-of-range model values are rejected even at zero depth. VCF model annotation validates allele INFO priors and writes the effective prior; separate input VCF priors override reusable PON priors. JSON wrappers retain constant-prior semantics. |
| Reference identity | Conflicting lengths/checksums fail on used contigs. Missing identity metadata yields `INSUFFICIENT_METADATA`, not `VERIFIED`, even if target REF bases agree. Rebuild when reference sequence or relevant inputs change. |
| Outputs | Existing generated Skua fields, files and stale output indexes require `--force`. Reannotation replaces generated fields while retaining unrelated annotations and genotype phasing. Reindex compressed VCF output after replacement. JSON optional file writes still overwrite directly. |
| Run metadata | Compact `SKUA_RUN` / JSON `run_summary` replaces the older provenance representation. Preserve exact input paths/hashes and workflow history externally; they are not recorded in this summary. |
| PON validation | Count declarations and values are checked consistently; CSI retrieval is compared with sequential target records. `pon inspect` can describe incompatible panels but does not certify them. |

## Previous PON artifacts

The compatibility decision is explicit: **only schema 2 / evidence policy 8**
is supported initially. Schema 1, policies 7 and earlier, unknown future
versions and panels without required reference or `IndelMatching` metadata are
not accepted. There is no automatic migration or legacy-policy execution.
Rebuild from original targets and normal alignments; editing version headers
cannot reconstruct corrected evidence. This applies even to an SNV-only panel
whose individual counts might happen to be unchanged by an indel fix.

Inspect, then validate a compatible panel (omit `--reference` only when no FASTA
check is intended; `--targets` checks the full ordered target list):

```bash
skua pon inspect hotspots.pon.bcf --json
skua pon validate hotspots.pon.bcf --reference reference.fa --targets hotspots.vcf.gz
```

For an incompatible panel, build a new artifact and annotate from it:

```bash
skua pon build --vcf hotspots.vcf.gz --normal-list normals.lst \
  --reference reference.fa --output hotspots.v1.pon.bcf
skua pon validate hotspots.v1.pon.bcf --reference reference.fa --targets hotspots.vcf.gz
skua annotate --pon hotspots.v1.pon.bcf --alignment case.bam \
  --reference reference.fa --output case.v1.vcf.gz
```

Keep original target/reference/alignment inputs available for future rebuilds.
Changing only truncation, pseudocounts, priors or assessment minima requires
reannotation, not rebuilding a compatible panel. See the complete
[rebuild decision table](../v1-contract.md#pon-compatibility-and-rebuild-decision).

## Release gates

The Stable classifier describes the bounded v1 contract; it is not a claim of
assay validation. Version and classifier updates are prepared together in this
release candidate. Publish only after review of the contract and migration
decision and successful validation of the revision being released:

1. Pass the full test matrix on Python 3.11–3.14 with current pysam, plus the
   minimum pysam 0.22.0 lane on Python 3.11.
2. Check source/Conda version agreement with
   `python scripts/check_release_version.py --tag v1.0.0`.
3. Build the Conda artifact and run its installed-package functional smoke test
   (`tests/artifact_smoke.py`) outside the source checkout. This exercises the
   installed CLI, live annotation, PON build/validate and cached annotation.
4. Require the publication workflow's exact-revision source validation and
   artifact tests to pass before uploading the versioned package.

The existing [tests](../../.github/workflows/tests.yml) and
[publication workflow](../../.github/workflows/publish.yml) enforce the test and
artifact sequence for PRs and releases. Preparing or merging this PR does not
publish a package; publication is triggered separately by the release tag.
